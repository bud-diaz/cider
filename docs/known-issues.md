# Known Issues

This is the Stage 5 alpha-track known-issues database. It records user-visible limitations that should be visible before someone tries Cider, even when they are not security vulnerabilities.

| ID | Area | Status | Impact | Workaround / Next step |
| --- | --- | --- | --- | --- |
| CIDER-KI-0001 | UI showcase manual polish | Open | `examples/ui-showcase` builds and primitives are tested, but the full app has not had an exhaustive human tap-through pass under `cider run`. | Run and record a manual UX pass before public alpha. |
| CIDER-KI-0002 | Text input | Open | X11 basic text input works for simple keymap text, but full XIM/XIC/IME composition and dead keys are not implemented. | Use ASCII/basic text while running under Cider; implement composed input before claiming broader text support. |
| CIDER-KI-0003 | Compatibility scanner | Open | `cider scan` is token-based, not a Swift parser. It can miss dynamic/aliased framework usage and only knows registered symbols. | Keep registry entries explicit; consider SwiftSyntax when scanner precision becomes a blocker. |
| CIDER-KI-0004 | Dev console proxy scope | Open | `cider dev` request capture is loopback-only and scoped to `CiderHTTP`; it is not a system-wide proxy. | Use `CiderHTTP` in reference apps for inspectable network calls. |
| CIDER-KI-0005 | File watching | Open | The dev console uses polling and rebuild/relaunch, not in-process Swift hot swap. | Use `cider run --no-build` and `cider dev` for faster loops; do not expect hot reload. |
| CIDER-KI-0006 | Reference app count | Closed | 10 reference applications now exist under `examples/`, each building in CI. | None; keep new apps narrow-scope per `docs/06-testing-strategy.md` section 7. |
| CIDER-KI-0007 | Public packaging | Open | Cider has no signed binary archive or package-manager distribution yet. This is an accepted alpha caveat, not a gap that will close by itself; see `RELEASE_NOTES.md`. | Build from source per `docs/install.md` until packaging lands. |
| CIDER-KI-0008 | Security contact | Closed | `SECURITY.md` documents GitHub private vulnerability reporting as the public contact channel, and the feature is enabled on the repo. | None. |
| CIDER-KI-0009 | Lifecycle hooks have no interactive trigger | Open | `CiderApp.didEnterBackground()`/`didEnterForeground()` exist and are conformance-tested (`LIFE-BG-002`), but nothing in `cider run` itself drives a background/foreground transition -- there is no real OS app-switcher signal on Linux, and no CLI/dev-console control to simulate one interactively. `examples/lifecycle-cider`'s log will only ever show "Launched" outside of a test. | Drive transitions via `ApplicationRuntime.enterBackground()`/`enterForeground()` in tests/harness code; add an interactive trigger (dev-console button, signal handler) before relying on this for manual demos. |
| CIDER-KI-0010 | `CiderTimer` callbacks run off the render thread | Open | `CiderTimer.after`'s closure runs on a background dispatch queue (`compatibility/Sources/CiderUI/Services.swift`), not the runtime's pump loop. Mutating `@CiderState` from it is not synchronized with rendering, and `CiderState` is not `Sendable`, so Swift 6 strict concurrency requires an explicit opt-out (`nonisolated(unsafe)`) to capture it in the `@Sendable` closure -- found while building `examples/timer-clipboard-cider`, the first reference-app use of `CiderTimer`. | Hop back to the runtime's thread before mutating state, or make `CiderTimer`/`CiderState` genuinely thread-safe, before recommending this pattern generally. |
| CIDER-KI-0011 | `#filePath` embeds absolute build paths | Open | Every `CiderUI` view initializer and modifier records its call site through a defaulted `#filePath` (ADR 0006), so the absolute path of each source file is present in the built binary's string table. Debug builds already carried these in debug info; a release build of an application now carries them too. | Nothing yet. Strip or relativise the recorded path at build time before Cider is used for anything distributed. |
| CIDER-KI-0012 | The dev-console editor changes properties only | Open | `cider dev`'s editor writes property changes back into Swift source, but only where the value is written as a literal the rewriter can prove it understands (ADR 0008). Expressions, named constants, interpolated strings, theme colours and multi-line argument lists are refused with a diagnostic rather than rewritten. It never adds, deletes or reorders views: `NodeID` is a structural path, so inserting a sibling re-keys every following node. Each accepted edit rebuilds and relaunches, so application state resets. | Edit the refused cases by hand. Structural editing needs developer-supplied node keys first, as ADR 0003 anticipated. |
